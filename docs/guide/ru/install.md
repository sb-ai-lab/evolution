# Установка

[English](../install.md) · Русский

К концу этой страницы Lab и Evolution Core будут установлены в виртуальное
окружение, а вы выполните полную фиксированную оценку синтетического агента —
без LLM, сети и ключей API, за несколько секунд.

Если вы ещё не читали [Как работает Lab](concepts.md), сначала просмотрите эту
страницу: здесь используются термины *Target Service*, *Bundle*, *пара версий* и
*conformance*.

## Что понадобится

- **Linux или macOS.** В Linux используется child subreaper. На macOS Lab совмещает группу процессов, опрос дерева каждые 0,5 с и метку окружения. На macOS процесс может пережить остановку, если выйдет из группы, исчезнет из дерева между опросами и скроет метку окружения. Windows не поддерживается.
- **Python 3.12 или 3.11** (Lab поддерживает версии ≥ 3.11.4).
- **[uv](https://docs.astral.sh/uv/)** для сборки wheel и создания виртуального
  окружения и **[just](https://just.systems/)** для запуска рецептов установки.
- **git** с доступом на чтение к репозиторию Lab.
- **Core.** Исходный код нужной версии Core входит в публичный репозиторий.
- Однократный доступ к сети, чтобы uv получил backend сборки и зависимости с PyPI.

## Заметки для macOS

Текущая пара поддерживает macOS и Linux.

Установка из checkout собирает Core из локального репозитория. На macOS используйте `shasum -a 256` вместо `sha256sum`.

Путь сервисного сокета может занимать не более 103 байт на macOS (107 на Linux). У `$TMPDIR` бывает длинный префикс: при необходимости передайте `--socket` с более коротким путём в приватном каталоге 0700. Предок-ссылка, например `/tmp`, допустим; сам корень состояния, scratch или home должен быть настоящим каталогом.

## Почему нужна сборка из исходников

Ни один пакет пока не опубликован на PyPI. Этот checkout использует **пару версий**:

```text
evolution-lab 0.0.3.dev81  +  evo-skills 2.0.0b22 (exact)
```

См. [пару текущего снимка](../../../lab/docs/RELEASES.md). Для старых прогонов используйте породившие их checkout и wheel. Для каждой пары создавайте новый каталог
состояния: состояние Owner не переносится между парами. Общий реестр проектов
Lab home обновляется [отдельными аддитивными обновлениями](../../../lab/docs/api/projects.md#the-lab-home).

Сохраните оба wheel-файла после установки. Lab позже запросит пути к ним:
Bundle записывает точные архивы wheel, из которых построено окружение, а Lab
повторно проверяет их перед каждым прогоном.



## Установка с just

Из `lab/` в клоне `sb-ai-lab/evolution`:

```sh
just setup      # core built from this repository
just demo       # the offline example from Step 5, checked and explained
```

`just setup` берёт закреплённые версии из `pyproject.toml` (`evo-skills==…` в
`dependencies`), поэтому при смене пары его не нужно редактировать. Команда:

1. **Собирает wheel Core** в `.lab/wheels/core-<commit>/`. Lab лежит в `lab/`
   репозитория Core; коммит — последний, менявший что-либо вне `lab/`, поэтому
   коммиты только в Lab оставляют тот же wheel Core. Команда экспортирует файлы
   этого коммита (без `lab/`) через `git archive` и собирает там wheel. Незакоммиченные изменения Core перечисляются и в wheel не
   попадают; рабочее дерево не изменяется. Если версия Core в этом коммите не
   совпадает с закреплённой в Lab, команда останавливается и называет обе
   версии. Если wheel для коммита уже есть, сборка пропускается.

   После коммита, меняющего Core, каждый рецепт, запускающий Lab, отказывает,
   пока `just setup` не установит Core этого коммита. Для установки используйте полный checkout.
2. **Собирает wheel Lab** из этого checkout, включая незакоммиченные изменения,
   в `.lab/wheels/`. Сборка воспроизводима: неизменённый checkout даёт тот же
   файл, и setup оставляет его как есть.
3. **Создаёт `.lab/venv`** с Python 3.12 (`just python=3.11 setup` для 3.11;
   venv на другом Python пересоздаётся) и устанавливает оба wheel с extras
   `[tree]`, `[service]` и `[mcp]`, каждый раз переустанавливая их для соответствия
   установленных файлов wheel.

Повторяйте `just setup` после каждого `git pull` или изменения кода Lab.

Wheel Core, собранный из репозитория, содержит тот же код, что wheel выпуска
этой версии, только если исходники Core не менялись после тега выпуска; даже
тогда SHA-256 архива отличается (метаданные и сжатие). Lab работает
с обоими. Bundle записывает хеш архива, поэтому digest Bundle с самостоятельно
собранным Core отличается от digest с wheel выпуска.

`just demo` сохраняет рабочее пространство в `.lab/demo/evaluation/`, а
`just demo-campaign` запускает пример кампании; оба описаны в разделе [Демо](demo.md).
Другие рецепты: `just serve` запускает [локальный сервис](cli.md) в
`~/lab-state/<pair>` (для этой пары `~/lab-state/dev81-b22`) с заполненными
аргументами `--execution-wheel`; `just panel --open` запускает для него
[панель](panel.md); `just lab <command>` выполняет любую команду `lab` из
`.lab/venv`; `just versions` показывает закреплённую пару, установленные версии и пути к wheel. `just` перечисляет все рецепты.

## Ручная установка

Ручные шаги в разделе [Ручная установка](#ручная-установка) используют один
рабочий каталог со следующей структурой:

```text
work/
  evolution/        a checkout of the public Evolution snapshot (Lab is in lab/)
  wheels/           the core wheel and the built Lab wheel
  lab-venv/         the virtual environment
```

Следующие шаги делают то же, что `just setup`, без just, в выбранной вами
структуре — например, при установке Lab в существующее окружение или получении
wheel Core из каталога передачи.

<a id="шаг-1-получите-wheel-ядра"></a>

### Шаг 1: Получите wheel Core

Соберите Core из публичного репозитория.

```sh
mkdir work && cd work
git clone https://github.com/sb-ai-lab/evolution.git
mkdir wheels
uv build --wheel -o "$PWD/wheels" evolution
```

### Шаг 2: Соберите wheel Lab

Используйте тот же checkout. Продолжите из `work/`, рядом с каталогом `wheels/`.

```sh
cd evolution/lab
git rev-parse HEAD                   # record this source revision with the wheel
uv build --wheel -o ../../wheels       # → evolution_lab-0.0.3.dev81-py3-none-any.whl
cd ../..
sha256sum wheels/evolution_lab-0.0.3.dev81-py3-none-any.whl
```

Wheel, повторно собранный из того же коммита, может иметь другой хеш архива.
Сохраните свою ревизию исходников и хеш вместе с wheel; при наличии сравните
артефакты поставки с [RELEASES](../../../lab/docs/RELEASES.md).

Wheel Lab содержит только Python-пакет в `src/evolution_lab/` (включая гайды).
Коммиты только документации вне `src/` не меняют содержимое пакета; правки
поставляемых гайдов меняют. Сборка и хеширование wheel не проверяют его: это
делают шаги 4 и 5.

### Шаг 3: создайте окружение и установите пакеты

```sh
uv venv -p 3.12 lab-venv
uv pip install --compile-bytecode -p lab-venv/bin/python \
  "evo-skills[tree] @ file://$PWD/wheels/evo_skills-2.0.0b22-py3-none-any.whl" \
  "$PWD/wheels/evolution_lab-0.0.3.dev81-py3-none-any.whl[service,mcp]"
```

При необходимости используйте `3.11` вместо `3.12`. Форма `file://` требует
абсолютного пути, поэтому используется `$PWD`.

В dev78 появились чтение по MCP и подключение из рабочего пространства. В dev79 ассистент может выполнять действия, например запускать кампанию и записывать подтверждение.
В [руководстве по MCP](mcp.md) описано подключение из рабочего пространства и через плагин,
а также проверка возможностей вашей сборки Lab.

#### Extras: что добавлять и зачем

*Extra* — необязательная группа зависимостей, добавляемая в квадратных скобках.

| Extra | Пакет | Добавляет | Когда устанавливать |
|---|---|---|---|
| `[tree]` | `evo-skills` | `httpx` и `openai` | Всегда, как выше. Они нужны роли Редактора Core на базе модели (`chat`). |
| `[service]` | `evolution-lab` | `fastapi`, `uvicorn` | Для локального сервиса `lab serve` или управления Lab через него инструментом вроде auto-evolve. |
| `[gateway]` | `evolution-lab` | `fastapi`, `uvicorn` | Для бюджетного шлюза — HTTP-прокси с ограничением расходов на LLM (см. [Бюджет и контроль расходов](budget.md)). |
| `[mcp]` | `evolution-lab` | MCP SDK (`mcp>=2.3,<3`) | Чтобы подключить ассистента к работающему Lab по MCP. См. [настройку MCP](mcp.md). |

`[service]` и `[gateway]` сейчас устанавливают одни и те же два пакета, поэтому
любой из них включает обе возможности. Всё равно указывайте нужный вам extra:
списки могут разойтись. Для установки обоих: `...whl[service,gateway]`.

Без `[service]` Python API и команды вроде `lab guides` работают обычно; только
`lab serve` отказывается запускаться с сообщением
`The service requires the optional service dependencies.`

#### Почему wheel, а не установка в режиме редактирования

Возможно, вы ожидаете `pip install -e .` из checkout Lab. Не используйте его
для реальной работы по двум причинам:

1. **Lab запускает код в изолированных подпроцессах.** Core, ваш target и
   workers Lab запускаются как `python -I ...`. Флаг `-I` игнорирует
   `PYTHONPATH` и текущий каталог, поэтому эти процессы всегда импортируют
   *установленный* пакет, а не папку `src/`.
2. **Lab проверяет установленные файлы.** Перед запуском Owner побайтово
   сравнивает установленные файлы Lab и Core с архивами wheel, записанными в
   Bundle. При editable install установленной копии файлов wheel нет, поэтому
   соответствия нет: Lab отказывает с `environment_invalid` при создании
   Bundle и перед запуском, если окружение после этого изменилось.

При изменении кода Lab пересоберите и переустановите wheel.

### Шаг 4: проверьте установку

Выведите список гайдов, поставляемых внутри wheel:

```sh
lab-venv/bin/lab guides list
```

Должны появиться восемь строк, по одной на гайд, начиная с
`evolution-lab-budget`. `lab guides path` выводит место установки, чтобы их
можно было открыть в Редакторе.

Проверьте пару версий:

```sh
lab-venv/bin/python -c "import importlib.metadata as m; print(m.version('evolution-lab'), m.version('evo-skills'))"
# 0.0.3.dev81 2.0.0b22
```

У `lab` нет флага `--version`; команда выше — надёжный способ проверки.

При желании посмотрите каталог требований — список того, что нужно пакету
эксперимента:

```sh
lab-venv/bin/lab guides requirements --json
```

В dev79 каталог сообщает `"catalogue_version": 13` и `digest`, начинающийся
с `7249ffee`. Названия пунктов на русском, поскольку приложение auto-evolve
показывает их пользователям; гайды объясняют каждый пункт по-английски.

### Шаг 5: запустите офлайн-пример

`examples/owner/evaluation.py` проходит полный путь фиксированной оценки на
агенте-заглушке, который отвечает без модели.
За несколько секунд он:

1. записывает в новый каталог исходников шаблон проекта (агент, адаптер,
   корпус, оценщик и файл запуска), как `lab new-project`;
2. фиксирует его в Bundle и готовит оценку трёх кейсов по одному образцу;
3. запускает агента как target и выполняет conformance, после которого target
   останавливается;
4. запускает новый target, выполняет фиксированную оценку и читает отчёт;
5. останавливает target и выводит сводку JSON.

Запустите из `work/`, рядом с checkout:

```sh
lab-venv/bin/python evolution/lab/examples/owner/evaluation.py \
  --python lab-venv/bin/python \
  --lab-wheel wheels/evolution_lab-0.0.3.dev81-py3-none-any.whl \
  --core-wheel wheels/evo_skills-2.0.0b22-py3-none-any.whl \
  --state-directory lab-state-example \
  --source-directory example-source \
  --port 18765
```

Три правила для аргументов:

- `--python` должен указывать на тот же интерпретатор, который запускает скрипт,
  а его путь не должен содержать `..`: Lab сравнивает его с путём, который
  интерпретатор сообщает о себе, и `../lab-venv/bin/python` приводит к
  `environment_invalid`. Запускайте из `work/`, как выше, или укажите абсолютный путь.
- `--state-directory` и `--source-directory` **ещё не должны существовать** и
  должны быть отдельными деревьями. Lab создаст их.
- `--port` должен быть свободен на `127.0.0.1`; там слушает target.

#### Как выглядит успех

Скрипт выводит сводку JSON. Проверьте поля:

| Поле | Ожидается | Что это означает |
|---|---|---|
| `conformance.state` | `"succeeded"` | Target прошёл тесты протокола Core. |
| `evaluation.coverage` | `{"expected": 3, "scored": 3}` | Запланированы 3 кейса × 1 seed, оценены все 3 образца. |
| `evaluation.report_state` | `"available"` | Отчёт измерения доступен для чтения. |
| `final_target.state` | `"stopped"` | Target корректно остановлен. |
| `blocker_count` | `0` | Ничего не осталось в ожидании очистки. |

Вы также увидите блоки `process`, `cleanup` и `persistence`. Lab намеренно
сообщает эти факты отдельно: процесс может корректно завершиться, пока очистка
ещё не подтверждена, и одно не заменяет другое.

Полные отчёты, корпус и записи диалогов остаются приватными в каталоге
состояния; скрипт выводит только сводные факты. [Первая оценка](first-evaluation.md)
показывает измерение своего агента с `lab new-project` и `lab evaluate` и
пошагово разбирает тот же скрипт. Состав
файлов примера и порядок их просмотра — в [Обзоре примеров](examples.md).

Для повторного запуска выберите новые имена каталогов или сначала удалите старые.

> **Новое в 0.0.3.dev72.** Пример создаёт проект из шаблона. Для своего
> агента создайте проект через `lab new-project`, подключите агента и выполните
> `lab evaluate` ([первая оценка](../first-evaluation.md#measure-your-own-agent)).
> В 0.0.3.dev71 и ранее пример использовал заготовку Core: два кейса с двумя
> seed, `{"expected": 4, "scored": 4}`.

### Устранение неполадок

**`RuntimeError: state and source directories must both be fresh`**
Один из двух каталогов уже существует — часто после предыдущего прогона,
остановившегося на середине. Выберите новые имена или удалите старые каталоги.

**`RuntimeError: target_start did not succeed: failed`**
Target не удалось запустить. Частая причина — занятый порт: проверьте через
`ss -ltn | grep 18765` и выберите другой `--port`. Неудачный прогон уже создал
оба каталога, поэтому для повтора используйте новые имена.

**`RuntimeError: run this example with the same interpreter passed as --python`**
Вы запустили скрипт одним Python, а в `--python` передали другой. Используйте
один и тот же `lab-venv/bin/python` в обоих случаях.

**`PreparationError: A declared environment does not match its identity.`**
(код `environment_invalid`) Переданные wheel отличаются от установленных в
окружении — например, wheel Core другой версии или wheel Lab другой сборки.
Передайте ровно два установленных wheel и убедитесь, что окружение содержит
соответствующую пару. Lab не смешивает пары. Та же ошибка появляется, когда
путь `--python` содержит `..`, например `../lab-venv/bin/python`; запускайте
из `work/` или передайте абсолютный путь.

**`PreparationError: A declared environment is unavailable.`**
(код `environment_unavailable`) Интерпретатор в `--python` не является
пригодным виртуальным окружением с установленным Lab, например это системный Python.

**`PreparationError: The preparation request is invalid.`**
(код `invalid_request`) Сам запрос некорректен; в примере типичная причина —
один и тот же wheel для `--lab-wheel` и `--core-wheel`.

**`The service requires the optional service dependencies.`**
Вы запустили `lab serve` без extra `[service]`. Переустановите wheel Lab с `[service]`.

**Windows**
Используйте машину, виртуальную машину или контейнер с Linux. Lab поддерживает Linux и macOS.

**Перед обновлением**
Перед обновлением завершите или остановите каждый незавершённый прогон с
манифестом `/15` на породившей его паре. Сохраните wheel, окружение и состояние
для чтения и очистки; новую работу начинайте с новым состоянием для новой пары.
Прогон, интерпретатор роли которого находится внутри seed, также должен быть
завершён или остановлен на старой паре: начиная с b9 (включая b10) он
отклоняется как `program_inside_seed`. Для нового прогона перенесите объявленный
интерпретатор за пределы seed. Lab не предоставляет продолжение связанным
прогоном (`linked_run_unsupported`) или миграцию состояния.

При переходе dev58/b10 → dev59/b11 начните с нового состояния в
`~/lab-state/dev59-b11`. Сохраните старые прогоны с породившими wheel и
состоянием для чтения, продолжения и очистки. Миграции и runtime-проверки
неверной пары нет.

### Advanced: Core directly

Если b10 остановил кампанию `/16` с `CampaignInvariantViolated: invalid journal record`
после `reflection_failed` (исправлено в Core b11), начните новую кампанию
на dev59. Само Core может продолжить этот прогон после rebase версии-производителя
с помощью `evo tree authorize`, а затем той же команды `evo tree evolve`; это
возможность Core, а не поддерживаемый путь продолжения Lab. См.
[CHANGELOG Core b11, Upgrade](https://github.com/sb-ai-lab/evolution/blob/main/CHANGELOG.md) об исключении для зафиксированной попытки.

**Старые каталоги состояния другой пары**
Для каждой пары версий используйте новый каталог состояния. Dev81/b22 использует `~/lab-state/dev81-b22` и схему Owner 14, которая хранит подтверждения действий. Читайте, продолжайте и очищайте старые прогоны с породившими их wheel и каталогами состояния.

#### `lab evaluate` и `lab new-project`

Команды доступны с 0.0.3.dev72. Ошибка до начала запуска выводится одной
строкой JSON в stderr: код `code`, относящиеся к ней `file` и `field`, а для
секрета также `role`. Код выхода 2 означает проблему проекта, 3 — неудачный
запуск target либо ошибку Lab или окружения. Все коды — в разделе
[Exit codes](../first-evaluation.md#exit-codes).

**Код 2, `secret_missing`.** Переменная из `secret_names` в `launch.json`
(роль `target`) или `scorer.allowed_env` в `evaluation-input.json` (роль
`scorer`) не задана в оболочке. Задайте её через `export` и повторите запуск:
Lab читает секреты только из собственного окружения.

**Код 2, `project_invalid` или `marker_not_allowed`.** Файл проекта отсутствует,
содержит некорректный JSON или поле неверной формы. Сообщение называет файл и
поле. `"lab:auto"` разрешён только в девяти полях, где он есть в шаблоне.

**Код 2, `corpus_invalid`.** Core отклонило строку корпуса. До запуска Lab
использует загрузчик корпуса Core и сообщает причину и код Core: некорректный
JSON, отсутствующее или неизвестное поле, повторный `case_id` либо неверный тип.
`file` указывает корпус, `field` начинается с номера строки; для пустого
корпуса номер не указан. Поля описаны в [корпусе](../evaluation-inputs.md#cases-and-the-corpus).

**Код 2, `argument_invalid`.** Например, `--wheel …: no such file` или
`--python …: no such file`; `field` называет аргумент. Проверьте путь.

**Код 2, `conflicting_values`.** Два поля, которые должны совпадать, содержат
разные явные значения, например `launch.json:endpoint.base_url` и
`evaluation-input.json:target.base_url`. Уравняйте их или верните одному либо
обоим значение `"lab:auto"`.

**Код 2, отсутствие `--wheel`.** Передайте wheel Lab и Core, из которых они
установлены; `just evaluate DIR` передаёт их автоматически.

**Код 2, `directory_not_empty` в `lab new-project`.** Целевой каталог уже
содержит файлы. Ничего не записано; выберите новый или пустой каталог.

**Код 3, `environment_invalid`.** Переданные wheel не совпадают с установленными,
например передан Lab другой версии. Передайте ровно те два wheel, из которых
выполнена установка. При использовании `--python` они должны быть установлены
и в указанном окружении.

**Код 3, `cleanup_failed`.** Предыдущий запуск оставил в состоянии target или
задачу, а Lab не смог их очистить. Сообщение указывает каталог и блокер; новый
запуск не начался. См. [очистку и ручное освобождение](../results.md#cleanup-orphans-and-manual-release).

**Код 3, `target start not confirmed: target_unavailable`.** Процесс агента не
достиг готовности. После правок `adapter.py` или `my_agent.py` частые причины —
ошибка импорта, отсутствующая зависимость или исключение в `build`/`factory`.
Переменные окружения, которые читает агент, должны быть объявлены в
`launch.json`: target получает только объявленные `env` и секреты. Вывод
показывает последние строки `stderr.log` и путь к нему; полный журнал находится
в `.lab/state-<pair>/scopes/<id>/stderr.log`. Исправьте причину и повторите запуск.

**Код 3, `unexpected_error`.** Произошла непредвиденная ошибка, например
`PermissionError` при записи в каталог проекта. JSON указывает исключение,
`state` и `run_dir`, если они существуют. Исправьте причину и повторите запуск.

**Код 3 после начала запуска.** В конце будет `Measurement not accepted: <reason>`
или, если оценка не началась, `Run stopped: <reason>`, и `exit code 3`.
Например, результат не сохранён, очистка не подтверждена или подготовка отклонила
артефакты (`artifacts_invalid`) без указания строки корпуса. Откройте
`evaluate.log` в директории запуска: там шаги и каталог состояния. Lab выбирает
свободный порт; если `endpoint.base_url` задаёт порт явно, проверьте, что он свободен.
